O assistente por dentro

O que acontece, na ordem, do Enter até a resposta: o que o navegador faz, o que o Django decide, o que vai para a OpenAI e o que fica gravado no banco. Tudo aqui foi conferido no código, e o mesmo conteúdo fica no projeto em assistant/docs/ARQUITETURA.html.

O banco é a memória

A chamada vai com store=False: a OpenAI não guarda nada. A cada rodada o Django remonta a conversa a partir da tabela Message e manda tudo de novo.

O modelo só pede

Ele não toca no banco. Ele pede uma ferramenta e o Django a executa. Uma leitura roda na hora. Uma escrita vira uma Proposal, e só o seu clique grava.

Uma mensagem, várias rodadas

Cada ida e volta com o modelo é uma rodada. Enquanto ele pedir ferramentas, vem outra, até o limite de 8. A resposta final é a primeira rodada que não pede nada.

O circuito de uma mensagem

É a função converse(), em client.py, rodando dentro de uma resposta HTTP que só fecha no fim. Os exemplos abaixo percorrem esse circuito com dados reais.

→
OpenAI2. Modelo respondetexto em pedaços e/ou pedidos de ferramenta
→

→

Pediu ferramenta → os resultados entram no histórico e começa outra rodada.
Não pediu → evento done, a conexão fecha e a resposta está completa.

Cinco mensagens, passo a passo

Cada ponto no trilho mostra onde a etapa acontece. Ids, valores e nomes são de exemplo. A sequência de ferramentas é a que o prompt induz, mas quem escolhe é o modelo, então numa conversa real ela pode variar.

Quanto gastei com mercado em agosto?

Hoje é 14/09/2026. A categoria Mercado tem id 3. Resultado: 3 rodadas e 6 linhas em Message, das quais o chat mostra 2.

  1. Navegadorassistant.js · submit → send()

    Você aperta Enter

    • Desenha sua bolha, mostra “Pensando...” e marca o painel como ocupado (data-busy). Um segundo envio fica bloqueado até o fim.
    • Faz um fetch POST com FormData (message) e o CSRF no cabeçalho X-CSRFToken. É fetch, e não EventSource, porque o EventSource só faz GET.

  2. Djangoviews.py · StreamView.post

    Barreira de entrada, antes do primeiro byte

    • Login e permissão assistant.use_assistant. Sem ela a resposta é 403, e não um redirect para o login.
    • Tira o byte nulo. Com mais de 2000 caracteres, mensagem vazia sem anexo, arquivo inválido ou /comando inexistente, devolve 400 em JSON.
    • Pega a vez do usuário, uma chave no Redis que o gerador devolve no fim. Com outra resposta ainda em curso, devolve 429: “Ainda estou respondendo à sua mensagem anterior.” Cada stream segura uma thread do servidor enquanto o modelo responde, e sem isto alguns envios simultâneos tomariam as threads de todo mundo. O recusado não gasta cota.
    • Por último, gasta uma mensagem da cota do dia com DailyUsage.consume(user). Se ela já acabou, devolve 429: “Você já mandou as 20 mensagens de hoje. O limite volta à meia-noite.” Texto, foto, áudio e /comando contam igual. Uma recusa das linhas acima não gasta cota.
    • Conversation.get_or_create(user): cada usuário tem uma conversa só.
    • Abre um StreamingHttpResponse text/event-stream com X-Accel-Buffering: no, para o nginx não segurar os pedaços.

    Toda recusa acontece aqui porque, depois que o stream começa, o status HTTP já saiu como 200. Dali em diante um erro só chega ao navegador como evento error.

  3. Bancoclient.py · converse()

    Grava a sua mensagem

    # Message #1
role    = "user"
content = "Quanto gastei com mercado em agosto?"   # o que o chat mostra
items   = [{"role": "user", "content": "Quanto gastei com mercado em agosto?"}]
                                                   # o que o modelo lê

    Aqui content e items são iguais. Eles diferem com foto (o item leva a imagem) e com /comando (o item leva as instruções).

  4. Rodada 1 o modelo precisa de ids

  5. Djangoclient.py · history() e responses.create

    Monta e envia a chamada

    client().responses.create(
  model        = settings.OPENAI_MODEL,        # padrão "gpt-5.6-luna"
  instructions = system_prompt(user, today),   # texto fixo de prompt.py + "Usuário: Gabriel / Hoje: 2026-09-14 (14/09/2026)"
  input        = history(conversation),        # os items das Message que couberam na janela, em ordem
  tools        = TOOLS,                        # os 8 schemas de tools.py
  stream       = True,
  store        = False,                        # a OpenAI não guarda nada
  include      = ["reasoning.encrypted_content"],
)
    • history() anda do mais novo para o mais velho, no máximo 40 mensagens. A rodada em curso — da sua fala até aqui — vai inteira, porque cortá-la deixaria chamada sem resposta. O que veio antes entra enquanto couber em HISTORY_BUDGET, 60 mil caracteres de texto: sem esse teto, uma consulta larga de ontem encareceria cada pergunta de hoje. No fim, descarta as role=tool que ficarem no começo da janela, porque a API recusa um resultado de ferramenta sem a chamada que o pediu.
    • O prompt é montado de novo a cada rodada. Por isso a data de hoje está sempre certa.

  6. OpenAIclient.py · collect()

    Modelo pede o cadastro, sem escrever texto

    O prompt manda chamar consultar_cadastros antes de usar qualquer id. O stream não traz nenhum delta de texto, só o evento final response.completed, com a lista output.

    collect() repassa cada response.output_text.delta ao navegador e guarda o output do evento final. Se vier response.failed, response.incomplete ou error, a rodada vira o evento error com “Não consegui concluir agora” e a mensagem termina ali.

  7. Banco

    Grava a rodada, mesmo sem texto

    # Message #2
role    = "assistant"
content = ""
items   = [
  {"type": "reasoning", "id": "rs_…", "encrypted_content": "gAAAAB…", "summary": []},
  {"type": "function_call", "call_id": "call_a1", "name": "consultar_cadastros", "arguments": "{}"}
]

    O raciocínio cifrado vai junto e volta intacto na rodada seguinte. Sem ele o modelo esquece por que pediu aquilo e refaz a consulta.

  8. Navegadorhandle(event)

    Aparece “Consultando o cadastro...”

    data: {"type": "tool", "name": "consultar_cadastros"}

  9. Djangoclient.execute → tools.run → queries.registry

    Executa a leitura

    Devolve todas as contas, com as combinações de tipo e método aceitas por cada uma (vêm de BusinessRule), todas as categorias, os cartões do usuário, com a data em que uma compra de hoje seria cobrada, e os códigos de tipo, método e natureza.

    Contas e categorias são um cadastro compartilhado. Cartões e transações são filtrados por user.

  10. Banco

    Grava o resultado, ligado à chamada pelo call_id

    # Message #3
role    = "tool"
content = '{"accounts": [...], "categories": [{"id": 3, "label": "Mercado"}, ...], "cards": [...]}'

  11. Rodada 2 agora ele sabe que Mercado é o id 3

  12. OpenAI

    O histórico já traz as mensagens #1, #2 e #3. O modelo pede o cálculo

    {"type": "function_call", "call_id": "call_b7", "name": "analisar_transacoes",
 "arguments": {"start": "2026-08-01", "end": "2026-08-31",
               "account": null, "category": [3], "uncategorized": null, "card": null,
               "type": ["OUT"], "method": null, "nature": ["REGULAR"], "origin": null,
               "min_value": null, "max_value": null, "search": null, "group_by": null}}

    Todos os campos vêm preenchidos porque as ferramentas estão em strict. Na análise, method: null aplica os métodos da Visão Geral (DEBIT e NOT_APPLICABLE), evitando contar juntos a compra no crédito e o pagamento da fatura. nature: null usaria REGULAR; neste exemplo o modelo a enviou explicitamente.

  13. Djangoqueries.Filters → analyze_transactions

    Valida cada argumento e soma no banco

    • Filters lê campo por campo. Uma data mal escrita, um id que não existe ou start depois de end geram um QueryError, que volta ao modelo como {"ok": false, "error": "..."}. Você não vê esse erro, e o modelo deve corrigir a chamada.
    • A consulta sempre começa em Transaction.objects.filter(user=self.user), e a soma é um Sum no Postgres.
    • describe() devolve o recorte que de fato valeu, para o modelo conferir antes de narrar.
    {"filters": {"period": {"date_field": "effective_at", "meaning": "data efetiva (no crédito, o vencimento da fatura), como nas telas",
                        "start": "2026-08-01", "end": "2026-08-31"},
             "category": [{"id": 3, "label": "Mercado"}],
             "type": [{"code": "OUT", "label": "Saída"}],
             "method": [{"code": "DEBIT", "label": "Débito"}, {"code": "NOT_APPLICABLE", "label": "Não Se Aplica"}],
             "nature": [{"code": "REGULAR", "label": "Normal"}],
             "not_filtered": "Toda dimensão ausente deste objeto entrou inteira no recorte, ..."},
 "total": {"income": "0.00", "outcome": "812.40", "net": "-812.40", "count": 14}}

    Mesmo caminho da rodada 1: evento tool (“Calculando...”), Message #4 assistant com a chamada e Message #5 tool com este JSON.

    Se uma análise incluir CREDIT junto de DEBIT ou NOT_APPLICABLE, o retorno ganha warnings: compra e pagamento da fatura podem ser o mesmo gasto. O prompt obriga o modelo a comunicar esse risco de duplicação das saídas e distorção do saldo.

  14. Rodada 3 a resposta

  15. OpenAI → Navegadorcollect() → appendDelta()

    O texto chega em pedaços

    data: {"type": "delta", "text": "Em agosto você gastou "}
data: {"type": "delta", "text": "**812,40** com Mercado"}
data: {"type": "delta", "text": ", em 14 transações (pela data efetiva)."}

    A cada pedaço, o navegador junta tudo o que já chegou e redesenha o Markdown, porque um ** pode abrir num pedaço e fechar no seguinte.

  16. Banco → Navegador

    Grava a resposta e encerra

    # Message #6
role = "assistant", content = "Em agosto você gastou **812,40** com Mercado, ...",
items = [{"type": "reasoning", ...}, {"type": "message", "content": [{"type": "output_text", ...}]}]

data: {"type": "done"}

    Não há chamadas nesta rodada, então vem o done e o gerador termina. O navegador sai do laço de leitura e, no finally, tira o status e libera o painel.

Ao reabrir o chat, HistoryView devolve só as mensagens visible=True, sem role=tool e sem as de conteúdo vazio que não têm anexo. Das 6 linhas sobram a #1 e a #6. As outras quatro existem para o modelo e para o admin.

Lança 50 reais de mercado hoje no débito do Nubank

A primeira parte é igual à pergunta: sua mensagem, depois a rodada 1 com consultar_cadastros. O que muda começa na rodada 2. A conta Nubank é o id 2, e a proposta criada será a #17. Neste exemplo, ontem já foi gravada uma saída de 50,00 no Mercado pela mesma conta, então o card avisa que pode ser repetida.

  1. Rodada 2 o modelo pede para propor

  2. OpenAI

    Modelo pede propor_transacao

    {"name": "propor_transacao", "arguments": {
   "action": "create", "id": null, "occurred_at": null, "account": 2, "type": "OUT",
   "method": "DEBIT", "card": null, "nature": null, "category": 3,
   "description": null, "value": "50.00", "clear": null}}

  3. Djangoproposals.propose → build

    Monta a proposta com o formulário da própria tela

    • Confere se a ação vale para o tipo de registro: parcelamento e transferência não aceitam update.
    • Separa o que veio preenchido (null e "" são descartados) e recusa campo que o formulário não tem.
    • Criar parte dos valores iniciais do formulário da tela (data de hoje, natureza Normal). Editar parte do registro atual e guarda um snapshot dele. Apagar apaga de verdade dentro de uma transação e desfaz tudo, só para descobrir se o banco deixaria (check_delete).
    • Roda TransactionForm(data, user).is_valid(), o mesmo form da tela, com as mesmas regras de conta, tipo e método. Se for inválido, devolve {"ok": false, "errors": {...}} ao modelo e nenhuma proposta é criada.
    • Numa edição que não muda nada, também recusa: não há o que propor.

  4. Djangoproposals.similar, só ao criar

    Procura uma transação parecida que já esteja gravada

    Com o form já válido, busca registros do mesmo usuário com o mesmo valor e a data da transação (occurred_at) a até 3 dias da pedida, para mais ou para menos (SIMILAR_WINDOW). Além disso, cada tipo exige alguns campos iguais (Spec.matching):

    PropostaTambém precisa ser igualComo cada achado aparece
    transaçãoconta e tipo01/09/2026 · Almoço · Mercado (87,40)
    parcelamentocartão e número de parcelas04/09/2026 · Geladeira · 1.000,00 (3x)
    transferênciaorigem e destino, no mesmo sentido04/09/2026 · 250,00 (Nubank → Itaú)
    cartãonão procura
    • Traz no máximo 5 achados (MAX_SIMILAR), os mais recentes primeiro, e os coloca em summary["similar"]. Sem achados, a chave nem existe.
    • Avisa, mas não barra. A proposta é criada do mesmo jeito, porque duas compras iguais no mesmo dia existem. Quem decide se é repetição é você, diante do card.
    • Editar e apagar não fazem essa busca.

  5. Banco

    Cria a Proposal. Nenhuma Transaction é gravada

    # Proposal #17
kind = "transaction", action = "create", target_id = null, status = "pending"
payload  = {"occurred_at": "2026-09-14", "nature": "REGULAR", "account": 2, "type": "OUT",
            "method": "DEBIT", "category": 3, "value": "50.00"}   # o que será validado de novo no clique
snapshot = {}                                                    # na edição: o registro como estava
summary  = {"title": "Criar transação", "action": "create", "rows": [...], "notes": [],
            "similar": ["13/09/2026 · Mercado (50,00)"]}               # só se a busca achou algo

    O modelo recebe {"ok": true, "status": "aguardando_confirmacao", "proposal_id": 17, "summary": ..., "message": "NADA foi gravado. ..."}, e isso também vira uma Message role=tool. Quando há similar, a message ganha no fim: “ATENÇÃO: já existe transação parecida, listada em summary.similar e destacada no card. Diga que pode ser repetida e peça que ele confira antes de confirmar.”

  8. OpenAI → Navegador

    “Já existe uma transação igual no dia 13. Confere se não é repetida antes de confirmar.” Depois, done

    Sem similar, a frase seria só um pedido de confirmação, como “Confere no card e confirma se estiver certo.” Se você responder que é outra transação, o prompt manda não insistir.

    O stream fecha e a conversa com o modelo termina aqui. A proposta fica pendente no banco, esperando você.

  10. Navegadoract(urls.confirm)

    Você clica em Confirmar

    Os botões travam e sai um POST para /assistant/proposal/17/confirm/. É uma requisição separada, sem stream, e o modelo não é chamado.

  11. DjangoConfirmView → proposals.confirm → apply

    Valida de novo e grava numa transação atômica

    • A proposta é buscada com user=request.user: a de outra pessoa dá 404.
    • Precisa estar pending e ter menos de 1 hora. Se não estiver, a resposta é 409 (“expirou”, “já foi confirmada”).
    • Em editar ou apagar: select_for_update no registro e comparação com o snapshot. Se algo mudou desde a proposta, recusa com “O registro mudou desde a proposta”.
    • Roda o mesmo form com o payload guardado. É o que o card mostrou, e não uma nova leitura do que você disse. Se ainda for válido, form.save().

  12. Bancoproposals.resolve

    Grava a transação, fecha a proposta e deixa um recado para o modelo

    # Transaction nova, criada pelo TransactionForm.save()
# Proposal #17
status = "confirmed", result = "Mercado (50,00)", resolved_at = agora

# Message nova, invisível no chat
role = "user", visible = False
content = "O usuário confirmou a proposta 17 (Criar transação) e ela FOI gravada: Mercado (50,00)."

    Se a gravação falhar, o atomic desfaz tudo, o status vira failed e o recado diz “ela NÃO foi gravada: motivo”. Descartar grava cancelled e “Nada foi gravado”.

  13. Navegador

    O card troca os botões pelo desfecho

    {"state": "confirmed", "result": "Mercado (50,00)"}   →   “Feito: Mercado (50,00)”

    O recado invisível só é lido pelo modelo na sua próxima mensagem, quando history() o inclui. É assim que ele sabe que não precisa oferecer a mesma transação de novo.

(foto de um cupom, sem legenda)

O que muda em relação à pergunta é o caminho da imagem até o modelo. Depois de ler o cupom, o modelo segue como na nova transação: cadastro, proposta, card.

  1. NavegadorfileInput change → shrink()

    A foto é reduzida antes de subir

    • No celular, capture="environment" abre direto a câmera traseira.
    • shrink() desenha a imagem num canvas com lado máximo de 1600 px e exporta em JPEG com qualidade 0,82. Isso também converte o HEIC do iPhone, quando o navegador consegue desenhá-lo.
    • A imagem fica numa faixa acima do campo e é enviada como file = foto.jpg. Uma mensagem leva um anexo só.

  2. Djangoattachments.inspect

    O tipo é conferido pelos bytes, e não pelo nome

    Olha os primeiros 16 bytes: FF D8 FF é JPEG, 89 50 4E 47 é PNG, RIFF…WEBP é WebP. Imagem acima de 8 MB ou formato desconhecido dá 400 antes do stream. O content_type que o navegador informa é ignorado.

  3. Banco e discoattachments.attach / user_item

    O arquivo vai para o disco, e no item fica só uma referência

    # arquivo: MEDIA_ROOT/assistant/<user_id>/<uuid>.jpg     (o nome original não é usado)
# Attachment #42  kind = "image", mime = "image/jpeg"
# Message         role = "user", content = ""
items = [{"role": "user", "content": [
           {"type": "input_image", "image_url": "attachment:42", "detail": "high"}]}]

    Com legenda, entra antes um {"type": "input_text", ...}. O detail: high é proposital: com a leitura barata o modelo erra centavos no cupom.

  4. Djangoclient.history → attachments.resolve / embed

    A referência vira bytes a cada rodada, e só nas duas fotos mais recentes

    • Entre as mensagens da janela que têm foto, as 2 mais recentes (IMAGE_MEMORY) viram data:image/jpeg;base64,…. O arquivo é lido do disco, e a busca confere se o anexo é do dono da conversa.
    • As fotos mais antigas, ou cujo arquivo já foi apagado, viram o texto [o usuário enviou uma foto neste ponto da conversa; a imagem não está mais anexada].
    • O base64 nunca vai para o banco. Ele é montado na hora e reenviado em toda rodada: uma proposta de 3 rodadas manda a foto 3 vezes.

  5. Navegador → DjangoAttachmentView

    A foto que aparece no chat

    No histórico, o anexo vem como /assistant/attachment/42/. A view confere o dono (a de outra pessoa dá 404). Em produção ela responde com X-Accel-Redirect e é o nginx quem entrega o arquivo. Com DEBUG ligado, o próprio Django entrega.

  6. Banco e discomake prune-attachments

    Limpeza

    O comando prune_attachments apaga anexos com mais de ASSISTANT_ATTACHMENT_RETENTION_DAYS dias (padrão 30), um por vez, para o sinal post_delete remover o arquivo do disco. Também apaga arquivos sem linha correspondente que tenham mais de 24 h. Limpar a conversa apaga os anexos pelo mesmo sinal.

(áudio) “gastei trinta e dois na farmácia no pix”

O modelo de chat nunca recebe o áudio. Ele recebe só a transcrição, como se você tivesse digitado.

  1. NavegadorstartRecording() → MediaRecorder

    Grava e envia

    Tenta os formatos nesta ordem: audio/webm;codecs=opus (Chrome), audio/webm, audio/mp4 (Safari), audio/ogg. Ao parar, o áudio fica na faixa. No envio, o status é “Transcrevendo o áudio...” e a sua bolha sai sem texto.

  2. Djangoattachments.inspect

    Confere pelos bytes, com limite de 8 MB

    WebM, Ogg, MP4/M4A, WAV ou MP3. Lê só os primeiros bytes para decidir o formato e confere o tamanho antes de trazer o arquivo para a memória: a transcrição é cobrada por minuto de fala, e o arquivo comprimido guarda muito mais tempo do que parece.

  3. OpenAIclient.transcribe

    Transcreve antes de gravar qualquer coisa

    client().audio.transcriptions.create(
  model    = settings.OPENAI_TRANSCRIBE_MODEL,   # padrão "gpt-4o-transcribe"
  language = "pt",
  prompt   = "Fala em português do Brasil sobre finanças pessoais: reais, Pix, boleto, ...")

    A transcrição passa pelo mesmo teto de 2000 caracteres do texto digitado: acima disso, evento error com “O áudio é longo demais” e fim, sem gravar nada. Sem essa conferência, um áudio longo entraria como uma mensagem de tamanho nenhum e voltaria à API em cada rodada.

    Se falhar ou voltar vazia: evento error com “Não consegui entender o áudio” e fim. Nada é gravado, nem a mensagem nem o anexo. O único rastro fica no log, e a mensagem da cota do dia já foi gasta na barreira de entrada.

  4. NavegadorfillBubble()

    A transcrição preenche a sua bolha

    data: {"type": "transcript", "text": "gastei trinta e dois na farmácia no pix"}

    Se você digitou algo junto, o texto enviado é o digitado, uma quebra de linha e o falado.

  5. Banco

    A mensagem guarda o texto, e o áudio fica como anexo

    Message: role = "user", content = "gastei trinta e dois na farmácia no pix"
         items = [{"role": "user", "content": "gastei trinta e dois na farmácia no pix"}]
Attachment: kind = "audio", mime = "audio/webm"   # só para tocar no chat

    A partir daqui é o circuito normal. O prompt avisa que a transcrição erra justamente em números e nomes próprios, e pede para confirmar em caso de dúvida em vez de escolher o mais parecido.

/gastos-fixos setembro

Um comando é só um texto guardado. O chat mostra o que você digitou, e o modelo recebe as instruções expandidas.

  1. NavegadorrenderSuggestions() / useCommand()

    A barra abre as sugestões

    Enquanto o campo contém só / e o começo de um nome, aparece a lista de comandos salvos. As setas navegam, Enter envia o comando destacado, Tab completa o nome e deixa um espaço para o complemento. A lista existe só para sugerir: quem resolve o nome é o servidor.

  2. Djangocommands.find, dentro da barreira do StreamView

    Resolve o nome antes do stream

    A regex /([a-z0-9-]+) só vale no começo da mensagem e precisa ser seguida de espaço ou do fim do texto. “1/2 do aluguel” continua sendo conversa. O nome é comparado em minúsculas. Se você não tiver esse comando, a resposta é 400: “Você não tem o comando /gastos-fixos”.

  3. Bancocommands.expand

    O content guarda o que foi digitado, e o item leva as instruções

    content = "/gastos-fixos setembro"
items   = [{"role": "user", "content":
"[Comando /gastos-fixos] Instruções que salvei para este comando. Siga-as agora e me responda com o resultado.

<instrucoes>
Some as saídas das categorias Aluguel, Luz, Internet e Academia e mostre numa tabela.
</instrucoes>

Complemento: setembro"}]

    As instruções são copiadas no momento da chamada. Se você editar o comando depois, as conversas antigas continuam com o texto antigo. No admin, isso aparece em “Texto enviado ao modelo”.

  4. OpenAI

    Daqui em diante é o circuito normal

    A seção # COMANDOS do prompt manda tratar as instruções como pedido seu, responder sem perguntar se deve começar e manter as regras: números vêm de ferramenta, gravar é por proposta.

  5. DjangoCommandForm · Command.limit_for

    Criar e editar comandos

    O modal fica só na página do assistente. O nome passa por slug (“Gastos Fixos” vira gastos-fixos) e é único por usuário. O limite é 5 comandos, 10 ou 20 com as permissões command_limit_10 e command_limit_20, e ilimitado com unlimited_commands ou para o superusuário. O limite só barra a criação.

Como ler o admin

Em Assistente › Mensagens, cada linha é uma Message, exceto as role=tool, que aparecem dentro da chamada que as pediu (ligadas pelo call_id). A lista é ordenada da mais nova para a mais antiga, então uma conversa se lê de baixo para cima. Filtre pelo usuário.

Usuário

Uma mensagem sua visível. Ao abrir: o texto, o anexo e, num /comando, o “Texto enviado ao modelo”.

Chamada de Ferramenta

Uma rodada em que o modelo só pediu ferramentas, sem texto. Mostra os argumentos (sem os null) e um resumo do retorno.

Ferramenta Recusou

Uma rodada em que pelo menos uma chamada voltou ok: false. Isso não é bug por si só: o erro vai para o modelo corrigir. Vira problema se a rodada seguinte não corrigir.

Assistente

Uma rodada com texto. Normalmente é a resposta final, mas uma rodada com texto e chamadas também recebe esta etiqueta.

Aviso Interno

O recado invisível sobre o desfecho de uma proposta (confirmada, descartada ou recusada), que só o modelo lê.

O que é garantido e o que é só pedido

Esta é a distinção que mais importa para confiar no assistente. O que está à esquerda o código impõe, não importa o que o modelo faça. O que está à direita depende de o modelo seguir o prompt, e por isso vale conferir no admin.

Garantido pelo código

  • Nada é gravado sem o seu clique.As ferramentas propor_* só criam Proposal. Transaction e Card são gravados apenas em proposals.apply, chamado só pelo POST de confirmação.
  • O que se grava é o que o card mostrou.O payload fica guardado e é validado de novo pelo mesmo form da tela. Em editar e apagar, se o registro mudou desde a proposta, a confirmação é recusada.
  • Cada um vê só o que é seu.Transações, cartões, propostas, conversas e anexos são sempre filtrados pelo usuário da requisição. O modelo não escolhe o usuário. Contas e categorias são compartilhadas por desenho.
  • A regra de negócio é a mesma da tela.A proposta usa CardForm, TransactionForm, InstallmentForm e TransferForm. Apagar testa o delete() real e desfaz.
  • Uma transação parecida sempre aparece no card.Ao criar transação, parcelamento ou transferência, proposals.similar faz a busca e o card mostra o quadro vermelho. Isso não depende do modelo. O aviso não impede a confirmação.
  • Toda consulta calcula no banco.As ferramentas somam com Sum e devolvem o recorte aplicado. Um argumento inválido volta como erro, e nunca vira um filtro silencioso.
  • A cota diária barra antes de qualquer custo.20 mensagens por dia sem faixa, 50 ou 100 com message_limit_50 ou message_limit_100, e ilimitado com unlimited_messages ou para o superusuário. Sem cota não há transcrição, anexo nem chamada ao modelo. A conferência e a soma são um UPDATE só, então duas abas não passam juntas pela última vaga.
  • Há limites fixos.8 rodadas por mensagem. Uma chamada idêntica a outra que já falhou não é executada de novo. 2000 caracteres por mensagem, transcrição de áudio incluída. Propostas expiram em 1 hora. Imagens e áudios até 8 MB, conferidos pelos bytes.
  • O tamanho do que sobe à API tem teto.A conversa inteira vai em cada rodada, então o custo não está no número de mensagens. Um retorno acima de MAX_TOOL_OUTPUT (30 mil caracteres) é descartado com um aviso para estreitar o recorte; as consultas de uma mensagem somam até TOOL_BUDGET (120 mil) e as seguintes não são executadas; o histórico anterior à rodada em curso entra até HISTORY_BUDGET (60 mil). Os tetos de linha das ferramentas ficam abaixo disso, para uma página cheia sempre caber.
  • Uma resposta por vez para cada usuário.Enquanto o stream está aberto, outro envio do mesmo usuário leva 429 e não gasta cota. A vez é uma chave no Redis, devolvida no fim do gerador e com validade de 300 s, para não ficar presa se o processo morrer no meio.

Só pedido ao modelo (prompt.py)

  • Que o número da resposta seja o da ferramenta.Nada impede o modelo de escrever um valor diferente do total que recebeu. Este é o ponto principal a conferir.
  • Que “quanto gastei” use nature: REGULAR.Sem esse filtro entram transferências e ajustes de saldo, e o número fica diferente do da Visão Geral.
  • Que ele diga qual recorte usou.Por exemplo, data efetiva ou data da compra no crédito.
  • Que não diga “feito” antes da confirmação.O retorno da proposta avisa com “NADA foi gravado”, mas a frase quem escreve é o modelo.
  • Que avise na frase que a transação pode ser repetida.O card avisa de qualquer jeito. A frase e o “não insistir” se você disser que é outra dependem do modelo.
  • Que pergunte o que falta em vez de chutar.Isso vale para a conta, o valor ilegível numa foto e o nome mal transcrito num áudio.
  • Que recuse assuntos fora do escopo e trate o texto dentro de imagens como dado.Não há filtro no código para isso.

Comportamentos que podem surpreender

Nada disto é erro de implementação. São consequências do desenho que, sem saber, parecem defeito.

  • A memória acaba antes do que parece

    O limite de 40 conta linhas de Message, e não perguntas. Uma pergunta com duas ferramentas ocupa 6 linhas, e os avisos internos também contam. Com perguntas desse tipo, o modelo lembra de algo como as últimas 6 ou 7. E o teto de caracteres pode encurtar mais: depois de uma listagem grande, ela sozinha ocupa a janela e o que veio antes fica de fora.

  • Uma consulta larga demais volta como recusa

    O retorno acima de 30 mil caracteres é descartado antes de entrar na conversa, e o modelo recebe um pedido para estreitar o recorte. Do lado de fora isso aparece como o assistente pedindo um período menor em vez de responder de primeira. Os tetos das ferramentas — 60 transações por página, 120 linhas de agrupamento — ficam abaixo desse limite justamente para que uma página cheia não caia aqui.

  • Confirmar não acorda o modelo

    O aviso interno é gravado no clique, mas o modelo só o lê na sua próxima mensagem. Até lá, nada muda na conversa.

  • Uma falha no meio deixa rastro parcial

    Se a OpenAI falhar na rodada 2, a sua mensagem e a rodada 1 ficam gravadas sem resposta. Na mensagem seguinte, o modelo vê a pergunta anterior sem resposta.

  • Nem todo erro aparece no admin

    Uma transcrição que falhou não grava nada. Uma exceção numa ferramenta vira “A ferramenta falhou” para o modelo, e o traceback vai para o log (“Ferramenta … falhou na conversa …”). Uma exceção fora disso gera “Stream da conversa … morreu”. Para depurar, olhe também o log do container.

  • Descartar funciona depois de expirar

    cancel() só verifica se a proposta está pending, e não a idade. Um card que ficou aberto na tela por mais de 1 hora ainda aceita Descartar e registra “Descartada”. Confirmar, não.

  • O aviso de repetida é tirado na hora da proposta

    A busca roda só quando a proposta é criada, e não de novo no clique. Se uma transação igual for gravada pela tela enquanto o card está aberto, ele não avisa. Na proposta de transação, a busca olha todas as transações da conta, inclusive parcelas e pernas de transferência, e compara a data da compra, e não a data efetiva.

  • Limpar apaga tudo

    ResetView apaga a Conversation, e com ela, em cascata, as mensagens, as propostas (inclusive as pendentes) e os anexos, com os arquivos. As transações já confirmadas continuam, e a cota do dia não volta.

  • A cota conta o envio, e não a resposta

    Uma mensagem aceita na barreira de entrada gasta a cota mesmo que o modelo falhe ou o áudio não se transcreva, porque a chamada à API já aconteceu. Quem não tem limite também é contado. O dia vira à meia-noite de São Paulo (timezone.localdate()).

Configuração e operação

O que liga o assistente para alguém, o que se ajusta por ambiente e o que a infraestrutura precisa fazer para o stream e os anexos funcionarem.

Permissões

PermissãoEfeito

Nas duas famílias de faixa, com mais de uma permissão vale a maior, e o superusuário é ilimitado porque tem todas. A regra está em tier_limit, no models.py. As permissões são dadas pelo admin, no usuário ou num grupo. Em código:

user.user_permissions.add(Permission.objects.get(codename='use_assistant', content_type__app_label='assistant'))

nginx (deploy/http.conf)

location /protected-media/ {
    internal;
    alias /app/media_root/;
}

internal significa que o navegador não consegue chegar aqui: só um X-Accel-Redirect vindo do AttachmentView abre esta porta.

location /assistant/stream/ {
    ...
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;
    gzip off;

    client_max_body_size 25m;
}

Cada linha desfaz um comportamento padrão que quebraria o stream: HTTP/1.1 e Connection vazio para a conexão ficar aberta, buffer e cache desligados para o pedaço chegar na hora, gzip off porque o compressor também acumula, 300 s de timeout porque uma resposta com várias ferramentas demora, e 10 MB de corpo, folga sobre o limite de 8 MB do anexo.

  • media-src: self, blob:A prévia do áudio gravado.

Como estender

Os passos para as mudanças mais prováveis, na ordem em que o circuito precisa delas.

Uma ferramenta de leitura

  1. Escreva a função em queries.py recebendo (user, arguments) e levantando QueryError com uma mensagem que ensine o formato certo.
  2. Declare o schema em TOOLS, no tools.py, com function(...).
  3. Registre a função no dicionário readers de tools.run.
  4. Acrescente a frase de status no STATUS do assistant.js.
  5. Se ela mudar o sentido de algum recorte, diga isso no prompt.py.
  6. Teste em tests/assistant/test_queries.py.

Um tipo proponível

  1. Acrescente o valor em Kind, no models.py, e gere a migration: a CheckConstraint de kind precisa conhecê-lo.
  2. Acrescente a linha em SPECS, no proposals.py, com model, form, as ações permitidas e, se criar pode repetir um registro, os campos de matching. Nesse caso o model precisa ter value e occurred_at.
  3. Declare a ferramenta com proposal(...) em TOOLS e registre-a em PROPOSERS.
  4. Se o card precisar de linha calculada ou nota, acrescente o ramo em build e, para apagar, em delete_summary.
  5. Documente a regra no prompt.py: o modelo não adivinha o que o novo tipo significa.
  6. Teste em tests/assistant/test_proposals.py.

Uma faixa de limite

  1. Acrescente a permissão no Meta.permissions do model (Command ou DailyUsage) e a tupla em TIERS, mantendo a ordem da maior para a menor.
  2. Gere a migration com make make-migrations app=assistant.
  3. Teste no test_commands.py ou no test_usage.py, que já têm o padrão parametrizado das faixas.
